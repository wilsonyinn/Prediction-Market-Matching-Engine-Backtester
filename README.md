# Prediction-Market Matching Engine & Backtester

A limit order book matching engine modeled on a prediction-market exchange (Polymarket's
CLOB), built in Python: proven correct with a rigorous test suite, benchmarked and
optimized, then used to backtest a simple market-making strategy against recorded
Polymarket data.

> Status: Phase 0-2 (engine, tests, benchmarking and optimization) complete. Phase 3
> (real data, replay, backtest) is next. This README will keep filling in per the
> project spec (`SPEC.md`) — pitch, architecture diagram, backtest results, and
> limitations.

## Development

```bash
make install   # create .venv and install dev dependencies
make all       # lint + typecheck + test
make cov       # test with coverage report
```

Optional extras: `pip install -e ".[tree]"` for `TreeBook` (a `sortedcontainers`-based
implementation used for the general-exchange comparison), `".[bench]"` for chart
generation, or `".[dev]"` for everything including both plus the test/lint toolchain.

See [`SPEC.md`](SPEC.md) for the full project spec and [`docs/DESIGN.md`](docs/DESIGN.md)
for every recorded design decision, including the full Phase 2 benchmark methodology
and optimization log.

## Benchmarking

```bash
make bench          # default matrix: balanced/deep_book/sweep_heavy, depths up to 10k-100k
make bench-full      # + naive at 100k (excluded by default: ~36s of setup alone)
make bench-memory     # tracemalloc-based memory measurement (separate process from latency)
make bench-report     # regenerate results/RESULTS.md from results/*.json
```

Four book implementations are compared: `NaiveBook` (O(n) reference), `ArrayBook`
(bounded price array), `ArrayBookBaseline` (a frozen pre-optimization snapshot, kept
permanently for before/after comparison), and `TreeBook` (`SortedDict`-based, the
general-exchange approach).
[`results/RESULTS.md`](results/RESULTS.md) is mechanically generated by
`bench.report` from every committed `results/*.json` — every workload, every
implementation, every depth, latency and memory both — and CI regenerates it from
the same inputs and diffs against what's committed, so it can never drift from the
underlying data. The table below is a **hand-picked highlight** of the single
clearest result (`deep_book`, where the O(n)-vs-O(1) divergence and the biggest
optimization win both show up most plainly), not an automated excerpt — curating
which numbers lead a README is an editorial choice, kept separate from the
full, mechanically-audited appendix.

**`deep_book` workload, `baseline` vs. `optimized` labels** — the cleanest O(n)-vs-O(1)
story, and the one Phase 2's four optimizations targeted:

**Methodology, honestly**: this ran on an unisolated consumer laptop (Apple M5, no CPU
pinning, no isolated cores), not a dedicated benchmarking rig — treat `p99` as the
highest generally meaningful percentile and `max` as dominated by OS scheduling noise.
Latency is per-command (an engine call may emit several events), measured via
`perf_counter_ns` with fields unpacked outside the timed window. Percentiles use
nearest-rank (never an interpolated value that was never actually observed), aggregated
across repeats as the *median of each repeat's own percentile* — not pooled samples —
so one repeat hit by background load can't own the reported number; every repeat's own
figures ship in the JSON so that choice is auditable. GC is frozen (`gc.freeze()`), not
disabled, before each repeat. Timer overhead (~42ns median, ~42ns resolution on this
machine) is recorded, never subtracted. Setup is replayed once per cell and each repeat
starts from a `copy.deepcopy` of the already-populated engine, not a re-replay — at
depth 100,000, `NaiveBook`'s setup alone (its `best()` is O(n)) takes tens of seconds,
so re-running it five times per cell would cost minutes for zero additional signal.
Naive above depth 10,000 is excluded from the default matrix for exactly that reason
(`--include-slow` to include it) — excluded, not silently dropped: it still appears in
the results JSON with `status: "excluded"` and its reproduction command. The phrase
"low-latency" does not appear anywhere in this project; only measured numbers and
ratios.

Four optimizations were applied to `ArrayBook`, one per commit, each profiled first,
benchmarked before/after against `ArrayBookBaseline` (a frozen snapshot of the
pre-optimization code) in the same process, and logged in `docs/DESIGN.md` win or not:
positional arguments in `RestingOrder.from_order` (~5-8% p50), a single `type(x) is not
int` check replacing a double-`isinstance` pattern in validation (measured smaller than
an isolated benchmark predicted — kept anyway as a lossless simplification), inlining a
per-side array-selection helper (~2-3%, kept despite missing the pre-declared 5%
threshold, given zero risk and a small bounded readability cost), and replacing the
per-level `OrderedDict` FIFO with an intrusive doubly-linked list on `RestingOrder`
(the clearest win: +10.9% throughput on `deep_book` at depth 100,000, and a **28%
reduction** in bytes-per-resting-order rather than the small increase the design
anticipated). One measured-but-rejected candidate is also recorded: removing the
runtime type-validation checks entirely would save 3-6% more but was not adopted,
since that guarantee — a malformed order rejects with an event instead of crashing —
is worth its cost.
